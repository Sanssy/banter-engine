# Raspberry Pi Deployment and Operations

This guide deploys Banter Engine as a long-running systemd service on a 64-bit Raspberry Pi OS installation. Run all commands on the Raspberry Pi unless a command is explicitly marked as a build-host command.

## Prerequisites

- Raspberry Pi OS 64-bit with systemd
- Network and DNS access to MPP and Discord
- A valid MPP token, Discord webhook URL, and challenge ID
- `sudo` access for installation

The deployed layout is:

```text
/opt/banter-engine/banter-engine          executable
/opt/banter-engine/resources/             read-only runtime catalog
/etc/banter-engine.env                    secrets and configuration
/var/lib/banter-engine/                   persistent snapshots
/etc/systemd/system/banter-engine.service service definition
```

## Build

Build directly on a 64-bit Raspberry Pi:

```sh
go build -trimpath -ldflags="-s -w" -o banter-engine ./cmd/banter-engine
```

Alternatively, cross-compile from another machine at the repository root:

```sh
GOOS=linux GOARCH=arm64 CGO_ENABLED=0 \
  go build -trimpath -ldflags="-s -w" -o banter-engine ./cmd/banter-engine
```

Transfer the binary, `resources/`, `.env.example`, and `deploy/banter-engine.service` to the Raspberry Pi before continuing.

## Install

Create a dedicated system account and directories:

```sh
sudo useradd --system --home /var/lib/banter-engine --shell /usr/sbin/nologin banter-engine
sudo install -d -o root -g root -m 0755 /opt/banter-engine
sudo install -d -o root -g root -m 0755 /opt/banter-engine/resources
sudo install -d -o banter-engine -g banter-engine -m 0750 /var/lib/banter-engine
```

If the user already exists, `useradd` reports an error that can be ignored. Install the application files:

```sh
sudo install -o root -g root -m 0755 banter-engine /opt/banter-engine/banter-engine
sudo install -o root -g root -m 0644 resources/opportunities.json /opt/banter-engine/resources/opportunities.json
sudo install -o root -g root -m 0644 deploy/banter-engine.service /etc/systemd/system/banter-engine.service
sudo install -o root -g banter-engine -m 0640 .env.example /etc/banter-engine.env
```

Edit `/etc/banter-engine.env` and replace both placeholder secrets. Keep `SNAPSHOT_DIR=/var/lib/banter-engine` so snapshots survive upgrades and service restarts.

Validate the unit and start it at boot:

```sh
sudo systemd-analyze verify /etc/systemd/system/banter-engine.service
sudo systemctl daemon-reload
sudo systemctl enable --now banter-engine
```

## Startup Validation

Confirm the service is enabled, active, and running as the dedicated user:

```sh
sudo systemctl is-enabled banter-engine
sudo systemctl is-active banter-engine
sudo systemctl status banter-engine --no-pager
sudo systemctl show banter-engine -p User -p MainPID -p NRestarts
sudo journalctl -u banter-engine -n 100 --no-pager
```

The journal must contain `scheduler started`. Configuration or catalog errors appear as structured `level=ERROR` records.

Validate the Discord webhook independently before waiting for a detected opportunity:

```sh
set -a
. /etc/banter-engine.env
set +a
curl --fail --silent --show-error \
  -H 'Content-Type: application/json' \
  -d '{"content":"Banter Engine deployment check"}' \
  "$DISCORD_WEBHOOK_URL"
unset MPP_TOKEN DISCORD_WEBHOOK_URL
```

Then confirm that the next real opportunity generated by Banter Engine reaches the same Discord channel.

## Reboot Validation

Run this check from a local console or with confirmed remote recovery access:

```sh
sudo reboot
```

After reconnecting:

```sh
sudo systemctl is-enabled banter-engine
sudo systemctl is-active banter-engine
sudo journalctl -u banter-engine -b --no-pager
```

The service must be active and the current-boot journal must show `scheduler started` without manual intervention.

## Graceful Shutdown

systemd sends `SIGTERM`, which the application handles through `signal.NotifyContext`:

```sh
sudo systemctl stop banter-engine
sudo journalctl -u banter-engine -n 30 --no-pager
```

The journal must contain `scheduler stopped`, and `systemctl status` must report a clean exit. Start it again with:

```sh
sudo systemctl start banter-engine
```

## Automatic Restart

The unit uses `Restart=on-failure`. Test it by terminating only the service process:

```sh
before=$(systemctl show banter-engine -p NRestarts --value)
sudo kill -s SIGKILL "$(systemctl show banter-engine -p MainPID --value)"
sleep 15
after=$(systemctl show banter-engine -p NRestarts --value)
printf 'restarts: %s -> %s\n' "$before" "$after"
sudo systemctl is-active banter-engine
```

The restart count must increase and the service must return to `active`.

## Snapshot Persistence

Snapshots are stored outside the release directory and owned by the service account:

```sh
sudo ls -la /var/lib/banter-engine
sudo find /var/lib/banter-engine -maxdepth 1 -type f -name '*.json' -exec sha256sum {} \;
sudo systemctl restart banter-engine
sudo find /var/lib/banter-engine -maxdepth 1 -type f -name '*.json' -exec sha256sum {} \;
```

Files must remain present after restart and reboot. Their checksums can change after a successful poll because they represent the latest MPP state.

## Network Recovery

Perform this test from a local console to avoid losing remote access:

1. Temporarily disconnect the Raspberry Pi network.
2. Wait longer than `POLL_INTERVAL`.
3. Confirm the journal records a failed run while the service remains active.
4. Restore the network without restarting the service.
5. Confirm a later poll logs `run completed`.

Useful commands:

```sh
sudo systemctl is-active banter-engine
sudo journalctl -u banter-engine -f
```

The engine handles polling errors without exiting, so normal network recovery does not require systemd or manual intervention.

## Routine Operations

```sh
# Follow logs
sudo journalctl -u banter-engine -f

# Restart after configuration changes
sudo systemctl restart banter-engine

# Inspect the effective unit
sudo systemctl cat banter-engine

# Inspect recent failures
sudo journalctl -u banter-engine -p warning --since today --no-pager
```

Never put the real environment file in Git or expose it in logs. Rotate the MPP token and Discord webhook immediately if either value is disclosed.

## Upgrade and Rollback

Keep the previous binary during an upgrade:

```sh
sudo cp /opt/banter-engine/banter-engine /opt/banter-engine/banter-engine.previous
sudo install -o root -g root -m 0755 banter-engine /opt/banter-engine/banter-engine
sudo install -o root -g root -m 0644 resources/opportunities.json /opt/banter-engine/resources/opportunities.json
sudo systemctl restart banter-engine
sudo systemctl is-active banter-engine
```

Rollback if startup validation fails:

```sh
sudo mv /opt/banter-engine/banter-engine.previous /opt/banter-engine/banter-engine
sudo systemctl restart banter-engine
```

Snapshot files remain compatible with rollback because they are not stored in the release directory.

## Troubleshooting

| Symptom | Check | Action |
| --- | --- | --- |
| Service does not start | `journalctl -u banter-engine -n 100` | Correct environment values, paths, permissions, or catalog validation errors. |
| `status=203/EXEC` | Binary path and architecture | Reinstall an executable Linux ARM64 binary. |
| Permission error on snapshots | `/var/lib/banter-engine` ownership | Restore ownership to `banter-engine:banter-engine` and mode `0750`. |
| MPP requests fail | DNS, clock, token, outbound HTTPS | Restore connectivity or rotate the MPP token; the next poll retries automatically. |
| Discord requests fail | Webhook smoke test | Replace an expired webhook and restart the service. |
| Repeated restart loop | `systemctl show ... -p NRestarts` | Stop the service, inspect the journal, fix startup configuration, then reset failures with `systemctl reset-failed banter-engine`. |
